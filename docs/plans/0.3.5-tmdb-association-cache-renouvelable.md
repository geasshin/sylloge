# Sylloge — lot 0.3.5 : association TMDB et cache renouvelable

> Statut : **Client HTTP, association, rendu et renouvellement automatique livrés. Clé embarquée par le développeur. Reste la QA native macOS avec une vraie clé.**
>
> Ce plan est la spécification active du lot. Il ne contient aucune clé ni valeur secrète.

## 1. Résultat utilisateur

Sylloge reste une bibliothèque Films locale et utilisable hors ligne. Une personne peut, pour un film déjà créé ou pendant sa création :

1. lancer une recherche TMDB ;
2. examiner plusieurs correspondances ;
3. choisir explicitement une œuvre ;
4. associer cette œuvre à sa fiche Sylloge ;
5. retrouver, aux ouvertures suivantes, une présentation enrichie avec affiche, résumé et casting, sans refaire le matching.

Cette présentation enrichie est un **cache TMDB renouvelable**, jamais la source de vérité de la bibliothèque. Quand le cache est indisponible ou expiré, la fiche personnelle reste intacte et utilisable avec son fallback visuel neutre.

## 2. Décisions actées

- **Fournisseur Films :** TMDB.
- **Clé API :** une **clé unique embarquée par le développeur** dans le binaire, fournie par Aurélien. Elle est stockée dans `src-tauri/src/tmdb/embedded_key.rs`, **ignorée par Git** (`.gitignore`), obfusquée par XOR, et jamais exposée au frontend ni aux exports. Ce choix remplace l'ancien modèle « une clé par utilisateur dans le Trousseau macOS », abandonné.
  - **Conséquence assumée :** l'application est destinée à un usage **gratuit et non commercial**, distribuée à des **personnes de confiance**. Toute distribution publique ou commerciale change la réglementation TMDB (licence commerciale requise) et impose de revoir ce modèle de clé.
- **Association :** explicite et humaine ; aucun matching automatique, aucune écriture avant le choix de la correspondance.
- **Appels réseau :** exclusivement depuis des commandes Rust. Le frontend appelle des commandes Tauri et ne reçoit jamais la clé.
- **Conservation :** `cache renouvelable`, et non donnée non persistante. Le cache source (y compris l’identifiant TMDB) a une durée opérationnelle maximale de 180 jours. Il devient éligible au rafraîchissement à partir de 80 jours.
- **Renouvellement automatique :** au démarrage de Sylloge, tous les caches dus sont rafraîchis en arrière-plan via une file séquentielle bornée. Aucun démon, service `launchd` ou tâche persistante n’est créé. Application fermée, aucune requête n’est envoyée.
- **Échec réseau :** le cache reste lisible jusqu’à son échéance ; à 180 jours, la ligne de cache est supprimée. La fiche personnelle reste disponible, mais l’utilisateur devra réassocier si aucun rafraîchissement n’a pu aboutir.
- **Images :** aucune image TMDB n’est téléchargée dans le dossier de données ou SQLite. Seules des URL distantes issues du cache temporaire sont rendues par l’interface.
- **Portabilité :** le cache TMDB et l’association ne figurent ni dans les exports/imports JSON ou CSV ni dans les snapshots. La copie d’un profil conserve seulement les données personnelles ; les associations sont refaites si nécessaire.
- **Attribution :** l'attribution TMDB est affichée dans « À propos », dans les réglages Application et à proximité de la présentation enrichie d'une fiche Film.

### Limite juridique explicitement assumée

Les conditions API TMDB interdisent de mettre en cache plus de six mois les informations obtenues via TMDB. Ce lot applique une purge au plus tard après 180 jours et une tentative de rafraîchissement anticipée. Il s’agit d’une stratégie prudente, **pas d’une confirmation écrite de TMDB qu’un renouvellement autorise une conservation indéfinie**.

## 3. Hors périmètre

- aucun serveur, proxy, compte Sylloge, synchronisation, cloud ou service payant ;
- aucune clé demandée, lue ou manipulée par un agent, et aucune clé saisie par l'utilisateur final ;
- aucun `VITE_TMDB_*`, `.env` runtime ou secret GitHub ; la clé est embarquée dans le binaire via `embedded_key.rs` (ignoré par Git), jamais dans le bundle frontend ;
- aucun téléchargement, recadrage ou conservation locale de fichiers image ;
- aucun changement du format d’export v1 ni migration des exports existants ;
- aucune fusion de profils ni écrasement de données personnelles ;
- aucune association automatique par titre ;
- pas de modèle durable de personnes, de rôles ou de galerie d’images dans la bibliothèque personnelle : le casting et les affiches font partie du cache de présentation ;
- pas de distribution publique ou commerciale dans ce lot. Le modèle de clé embarquée suppose une diffusion gratuite à des personnes de confiance.

## 4. État initial pertinent

- `src/main.tsx` orchestre le parcours « Enrichissement assisté » (recherche → candidats → confirmation → cache).
- `src/components/TmdbSearchFlow.tsx` et `src/components/TmdbAssociationConfirm.tsx` implémentent la recherche, la liste de candidats et la confirmation explicite.
- `src/data/tmdbService.ts` est la façade TypeScript des commandes Tauri ; elle ne contient aucune clé.
- `src/domain/film.ts` / `src/data/filmsRepository.ts` représentent les Films personnels dans SQLite ; les champs de provenance historiques font partie du format v1 et ne doivent pas devenir le nouveau cache TMDB.
- `src-tauri/src/tmdb/` contient le client HTTP (`client.rs`), le cache TTL (`cache.rs`), la clé embarquée (`embedded_key.rs`, ignorée par Git) et les commandes (`mod.rs`) ; `src-tauri/src/database.rs` contient les migrations séquentielles.
- `src/components/FilmDetail.tsx`, `src/components/Poster.tsx`, `src/main.tsx` et `src/styles.css` affichent la présentation enrichie.
- `src/components/Portability.tsx` rend les réglages, dont la section Application et À propos.
- Les exports/snapshots sont construits à partir du modèle Film personnel ; le cache TMDB reste absent de ce chemin.

## 5. Architecture cible

### 5.1 Frontière de secret

La clé TMDB est **embarquée côté Rust uniquement**. Elle est reconstruite à la volée depuis `embedded_key.rs` (fragments XORés), jamais stockée en clair, jamais envoyée au frontend. Les commandes Tauri exposées sont :

- chercher des films ;
- lire la présentation enrichie associée à un Film ;
- associer explicitement une correspondance ;
- demander un rafraîchissement non bloquant ;
- retirer une association ;
- purger les caches expirés.

Le backend :

1. reconstruit la clé en mémoire (jamais persistée ni affichée) ;
2. construit l’en-tête `Authorization: Bearer ***` ;
3. appelle TMDB par HTTPS ;
4. parse seulement le sous-ensemble nécessaire en DTO typés ;
5. ne logue ni secret, ni en-tête Authorization, ni URL contenant un token.

Le frontend reçoit les DTO métier et des erreurs utilisateurs génériques : réseau indisponible, recherche sans résultat, réponse fournisseur invalide ou limite temporaire.

### 5.2 Dépendances explicitement autorisées

Le lot peut ajouter, après vérification du lockfile :

- une liaison macOS minimaliste au Trousseau, compatible avec le MSRV déclaré `1.77.2` ; à la date de ce plan, `security-framework = 3.2.0` est MIT/Apache-2.0 et annonce Rust 1.70 ;
- un client HTTP Rust minimal avec TLS et JSON, compatible avec le MSRV ; à la date de ce plan, `reqwest = 0.12.12` est MIT/Apache-2.0 et annonce Rust 1.64 ;
- éventuellement `zeroize = 1.8.1` (MIT/Apache-2.0 ; Rust 1.60) pour réduire la durée de vie de la copie de clé en mémoire.

Ne pas activer de stores Linux, Windows ou navigateur non nécessaires dans ce lot. Épingler les versions suffisamment précisément pour ne pas relever accidentellement le MSRV. Inspecter le diff de `Cargo.lock` et ne pas accepter de script `build.rs` ou permission Tauri inattendu.

### 5.3 Schéma SQLite

Ajouter une migration suivante, sans modifier les valeurs de `films` ni les contrats d’export v1 :

```sql
CREATE TABLE film_tmdb_cache (
  film_id TEXT PRIMARY KEY NOT NULL REFERENCES films(id) ON DELETE CASCADE,
  tmdb_id INTEGER NOT NULL,
  language TEXT NOT NULL,
  payload_json TEXT NOT NULL,
  fetched_at TEXT NOT NULL,
  refresh_after TEXT NOT NULL,
  expires_at TEXT NOT NULL
);
CREATE INDEX film_tmdb_cache_refresh_idx ON film_tmdb_cache(refresh_after);
```

Contraintes de mise en œuvre :

- le cache contient la relation et la présentation TMDB ; il doit disparaître en une seule suppression ;
- les datations écrites et renvoyées sont UTC ISO 8601 canoniques au format `YYYY-MM-DDTHH:MM:SSZ` ;
- une lecture valide la langue canonique, les trois dates, leur ordre et les plafonds de 80 / 180 jours ; toute ligne incohérente est purgée puis signalée par une erreur métier générique ;
- les `CHECK` de la migration 8 bloquent seulement les formes textuelles manifestement non canoniques ; l’intégrité calendaire, l’ordre et les fenêtres restent obligatoirement contrôlés en Rust à la lecture ;
- le cache est remplacé atomiquement seulement après une réponse TMDB valide ;
- aucun cache ne peut être lu après `expires_at` ; la lecture purge immédiatement une ligne expirée ;
- les suppression de Film doivent supprimer le cache grâce à la clé étrangère ; activer/vérifier `PRAGMA foreign_keys = ON` dans le contexte réel SQLite si nécessaire ;
- le JSON ne reçoit qu’un DTO de présentation limité, jamais la réponse TMDB brute.

### 5.4 DTO de présentation minimal

Conserver uniquement ce qui est nécessaire à la présentation :

- identifiant TMDB, titre et titre original ;
- année/date de sortie, durée si disponible, synopsis, réalisateurs ;
- affiche principale, quelques affiches alternatives et leurs URLs distantes ;
- casting borné et déterministe : nom, rôle/personnage, URL distante de portrait éventuellement absente ;
- horodatages et langue du cache.

Borner explicitement le nombre d’affiches et de membres de casting envoyés à l’UI. Ne créer ni table Personne, ni table Rôle, ni fichier image durable dans ce lot.

## 6. Parcours et comportements

### Réglages

Dans Paramètres → Application, ajouter une carte « Métadonnées Films — TMDB » :

- état « clé absente » / « clé configurée » ;
- champ mot de passe vide pour saisir ou remplacer la clé ;
- action de suppression avec confirmation explicite ;
- texte honnête : clé stockée localement dans le trousseau, jamais dans les exports ou sauvegardes ;
- attribution TMDB et lien officiel.

Ne jamais relire, préremplir ou afficher la valeur existante.

### Association

- Le détail d’un Film propose « Associer à TMDB » quand aucune présentation valide n’est présente, et « Modifier l’association » sinon.
- Une recherche saisie par l’utilisateur affiche des candidats limités : affiche distante éventuelle, titre, titre original, année, synopsis bref.
- L’utilisateur sélectionne un candidat puis confirme l’association.
- Cette confirmation écrit uniquement `film_tmdb_cache`. Elle n’écrase jamais `title`, `summary`, `director`, `poster_url`, note, statut ou autre champ personnel du Film.
- Pendant la création assistée, le même sélecteur peut préremplir le formulaire, mais l’écriture finale dans les champs personnels reste lisible, modifiable et confirmée par l’utilisateur. La persistance de l’association doit être explicite dans ce parcours aussi.

### Affichage

- La bibliothèque peut employer l’affiche de cache lorsqu’elle est valide, sinon `posterUrl` personnel, sinon le fallback `Poster` existant.
- La fiche détail conserve les données personnelles et ajoute une section « Présentation TMDB » clairement identifiée, avec source/attribution, affiche, synopsis, réalisateurs et casting.
- Un cache dû reste affichable tant qu’il n’a pas atteint 180 jours. Une réouverture après trois mois doit donc pouvoir afficher le cache encore valide puis programmer silencieusement son renouvellement.
- Pendant que Sylloge est ouverte, tous les caches dus sont placés dans une file bornée de rafraîchissement, avec priorité aux Films visibles. Le traitement se fait en arrière-plan sans figer la bibliothèque ni bloquer l’affichage sur le réseau.
- Ici, « en arrière-plan » désigne uniquement une tâche interne à l’application ouverte. La fermeture de Sylloge arrête toute activité : aucun démon, service `launchd` ou tâche persistante ne continue les requêtes.
- En cas d’erreur de rafraîchissement, le cache valide reste disponible sans perdre la fiche locale.
- À expiration sans mise à jour réussie, purger et repasser au rendu personnel hors ligne.

## 8. Critères d’acceptation

- [ ] Une clé saisie dans l’interface ne se trouve dans aucun fichier du dépôt, export, snapshot, SQLite, log applicatif ou résultat de commande.
- [ ] Le frontend ne possède aucune API TMDB directe et ne reçoit jamais la clé.
- [ ] Un Film peut être associé manuellement à un candidat TMDB et garde cette relation après redémarrage tant que son cache est valide/renouvelé.
- [ ] La présentation de cache ne remplace aucune donnée personnelle sans action finale explicite de l’utilisateur.
- [ ] Les affiches et portraits distants ne sont pas téléchargés dans la bibliothèque locale.
- [ ] À J+79, `refresh_due` est faux ; à J+80, `refresh_due` est vrai. À J+180, un cache non renouvelé est supprimé et le fallback personnel est visible.
- [ ] Le renouvellement automatique traite tous les caches dus dans une file bornée lorsque Sylloge est ouverte, avec priorité aux Films visibles. Application fermée, aucune requête ne continue.
- [ ] Un échec réseau, une clé absente, une réponse invalide ou la suppression de la clé n’endommage jamais la fiche Film personnelle.
- [ ] Les exports/imports JSON et CSV historiques restent valides, et le cache n’est pas exporté.
- [ ] L’attribution TMDB est visible.
- [ ] L’interface reste navigable au clavier et avec les affiches/portraits absents.

## 10. Stop conditions

Arrêter et rapporter avant de contourner si :

- l’intégration native au Trousseau exige une permission non prévue ou une signature/entitlement incompatible avec la cible actuelle ;
- les dépendances compatibles MSRV ajoutent un build script, une permission ou une surface de stockage non explicitement examinée ;
- le cache ne peut pas être isolé des exports/snapshots existants ;
- une migration ne peut pas être validée sur des données SQLite contrôlées ;
- une condition TMDB observée exige une politique plus restrictive que ce plan ;
- le lot impose une persistance de personnes, d’images ou de métadonnées qui excède ce cache borné.
