# Sylloge 0.3.0 — lot interne 3 : updater Tauri signé

> **Statut :** prêt pour implémentation. Ce lot configure la vérification et l’installation de mises à jour Tauri depuis des releases GitHub signées. Il prépare une chaîne réelle, mais ne publie aucune release.
>
> **Branche :** `release/0.3.0-settings-updates`

## Résultat utilisateur

Dans **Paramètres → Application**, une personne peut :

- savoir que Sylloge consulte exclusivement des releases GitHub signées, jamais une branche Git ;
- vérifier manuellement les mises à jour ;
- activer ou désactiver la recherche automatique ;
- voir une mise à jour disponible avec version et notes ;
- choisir de télécharger/installer, de reporter ou d’ignorer cette version ;
- rétablir une version précédemment ignorée.

Une installation ne télécharge ni n’installe jamais un artefact dont la signature ne correspond pas à la clé publique Tauri embarquée. Tant qu’aucune release GitHub signée n’existe, l’interface le dit honnêtement et n’affiche aucun faux succès.

- **Publication :** manuelle et locale au départ. Aucun workflow GitHub Actions, compte Apple, token GitHub, release, tag, push ou changement de version ne fait partie de ce lot.

La clé privée `~/.tauri/sylloge-updater.key` et sa passphrase ne doivent jamais être lues, copiées, affichées, mises dans un fichier du dépôt, un `.env`, un document, une commande Codex, un test ou GitHub.

## Changements explicitement autorisés

### Dépendances et intégration native

Ajouter uniquement les plugins officiels Tauri v2 nécessaires :

- Rust : `tauri-plugin-updater` et `tauri-plugin-process` ;
- frontend : `@tauri-apps/plugin-updater` et `@tauri-apps/plugin-process`.

Initialiser les deux plugins dans `src-tauri/src/lib.rs` avec les autres plugins existants. Ajouter seulement les permissions nécessaires à la fenêtre principale : `updater:default` et `process:default`.

Dans `src-tauri/tauri.conf.json` :

- conserver le canal HTTPS ci-dessus ;
- intégrer la clé publique ci-dessus dans `plugins.updater.pubkey` ;
- activer `bundle.createUpdaterArtifacts: true` ;
- conserver `signingIdentity: "-"` ;
- ne jamais autoriser de transport HTTP non sécurisé.

### Préférences locales

Ajouter une migration SQLite séquentielle, après les migrations existantes, pour une table singleton de préférences d’updater applicatives. Elle contient au minimum :

- `automatic_checks_enabled` booléen, activé par défaut ;
- `ignored_version`, nullable ;
- `updated_at`.

La migration doit créer la ligne singleton sans modifier les profils, films, imports, exports, réglages de snapshots ou sauvegardes existants. Ajouter l’accès TypeScript ciblé nécessaire à la lecture et à la mise à jour de ces préférences, avec des valeurs typées et aucun SQL dynamique.

### Interface et comportement

Créer une couche frontend étroite pour appeler les API officielles `check`, `downloadAndInstall` et `relaunch` :

- à l’ouverture de l’application, déclencher une vérification silencieuse uniquement si la préférence automatique est active ;
- ne pas afficher d’alerte d’erreur intrusive si aucun manifeste de release n’existe encore ou si un contrôle silencieux échoue ; journaliser l’erreur pour diagnostic ;
- permettre une vérification manuelle depuis Paramètres, avec un statut compréhensible ;
- quand `check()` renvoie une update, afficher version, notes si présentes, et trois choix : installer, plus tard, ignorer cette version ;
- « Ignorer » persiste seulement cette version ; une version future n’est pas ignorée ;
- une mise à jour téléchargée est installée seulement après l’action explicite « Télécharger et installer », puis l’application redémarre via le plugin process ;
- l’option « Rechercher automatiquement » est persistée dans SQLite ; la page permet de rétablir une version ignorée ;
- gérer les états de chargement, téléchargement et erreur sans inventer une release ni prétendre qu’un 404 est une installation réussie.

Employer les conventions visuelles et d’accessibilité existantes dans `Portability.tsx` et `styles.css`. L’UI reste sobre : pas de faux pourcentage, pas de modal sans besoin, focus clavier et messages accessibles.

### Documentation de release

Compléter `docs/TAURI_UPDATER_SETUP.md` ou créer un document de release complémentaire qui décrit :

1. la première installation manuelle d’une version contenant l’updater ;
2. la préparation locale du build avec la clé privée conservée hors Git ;
3. les artefacts macOS attendus (`.app.tar.gz` et `.sig`) ;
4. le contenu obligatoire de `latest.json`, notamment la signature lue depuis le fichier `.sig` et l’URL GitHub de l’archive ;
5. l’upload manuel de l’archive, de `.sig` et de `latest.json` dans une GitHub Release versionnée ;
6. le test réel obligatoire sur une installation de test d’une version inférieure ;
7. la limite Gatekeeper sans Developer ID ;
8. l’interdiction de perdre ou tourner régulièrement la clé privée.

Un petit script Node sans dépendance peut être ajouté seulement s’il permet de générer de manière reproductible un `latest.json` à partir d’un fichier `.sig`, d’une version, de notes et d’une URL. Il doit être documenté, vérifié sur une fixture temporaire et ne jamais lire la clé privée.

## Exclusions strictes

- aucune lecture ou utilisation de la clé privée / passphrase ;
- aucune publication GitHub, GitHub Action, tag, commit, merge, push ou changement de version ;
- aucun Developer ID, certificat Apple, notarisation, compte payant ou identifiant Apple ;
- aucun serveur d’update, cloud de données, synchronisation, API culturelle ou permission réseau élargie ;
- aucune migration autre que les préférences singleton nécessaires à ce lot ;
- aucun faux test d’installation sans artefact réellement publié et signé.

## Critères d’acceptation

1. Les manifestes, dépendances Rust/JS et permissions compilent avec les plugins officiels Tauri v2.
2. Le bundle est configuré pour créer les artefacts d’updater et pour vérifier exactement la clé publique fournie, avec HTTPS GitHub Releases uniquement.
3. Les préférences d’updater survivent à une relance de la base locale, sont indépendantes des profils et ne régressent pas les migrations/sauvegardes existantes.
4. La vérification automatique respecte le choix utilisateur ; la vérification manuelle, l’ignorance et la réinitialisation sont accessibles.
5. Aucun téléchargement/installation ne démarre sans action explicite de la personne ; les erreurs et l’absence actuelle de release sont annoncées honnêtement.
6. La documentation permet à Aurélien de produire plus tard une release signée sans jamais exposer la clé privée.
7. `npm run typecheck`, `npm run verify`, `npm run build`, `cargo fmt --check`, `cargo check`, `cargo test`, `cargo clippy --all-targets -- -D warnings` et `git diff --check` passent.

## Preuves manuelles restantes

Après un vrai premier bundle signé et une GitHub Release de test, installer manuellement la version inférieure puis publier une version supérieure, signer les deux avec la même clé, vérifier la détection, l’ignorance, l’installation et le redémarrage. Cette preuve est impossible tant qu’aucun artefact signé n’a été produit et publié ; ne pas la simuler.
