# Sylloge 0.2.0 — sauvegardes JSON portables

> **Statut :** livré, revu et validé manuellement par Aurélien le 17 juillet 2026 ; prêt pour le commit et la fusion du jalon.
>
> **Branche :** `release/0.2.0-sauvegardes`, construite au-dessus des correctifs non fusionnés de `0.1.1` et `0.1.2`.

## Résultat utilisateur

Une personne choisit explicitement un dossier local de sauvegarde — qui peut être un dossier déjà synchronisé par iCloud Drive, Dropbox, Google Drive ou OneDrive — puis Sylloge y écrit des **instantanés JSON** de son profil Films :

- automatiquement, après le premier changement réussi de ce profil pour une journée locale ;
- à la demande, via un bouton **« Sauvegarder maintenant »** ;
- sans jamais copier ni synchroniser la base SQLite active, son WAL ou son SHM.

Le dossier sélectionné reste local à l’application. Si ce dossier devient indisponible, l’opération concernée signale le problème mais ne bloque jamais la création, l’édition, la suppression, l’import ou la sélection d’un profil.

## Décisions prises

| Sujet | Décision |
|---|---|
| Fréquence automatique | Premier changement réussi **par profil** et par journée locale. Cette granularité évite qu’un changement d’un second profil ne soit jamais couvert. |
| Action manuelle | Un bouton crée immédiatement un snapshot du profil courant, même si le snapshot quotidien a déjà eu lieu. |
| Conservation | Sylloge garde les **30 snapshots les plus récents par profil**. Un registre SQLite associe chaque fichier réellement créé à son profil ; la rétention ne supprime que ces entrées, jamais un fichier seulement ressemblant. |
| Contenu | Même JSON versionné `sylloge-films` v1 que l’export existant, donc réimportable dans un nouveau profil par le flux contrôlé actuel. Un snapshot porte sur le profil courant, pas sur une copie directe de la base SQLite. |
| Réglages persistants | Migration SQLite locale `backup_settings` : dossier choisi et dernier jour de snapshot automatique pour chaque profil. Aucun chemin n’est envoyé hors de l’appareil. |
| Écriture native | Commandes Rust limitées au dossier choisi explicitement dans l’interface. Aucun accès générique aux fichiers n’est accordé au frontend. |
| Échec | Pas de mise à jour du dernier jour après un échec ; une prochaine modification peut donc réessayer. Le message visible décrit le problème sans inventer une sauvegarde réussie. |

## Non-objectifs

- aucune synchronisation Sylloge, aucun compte, cloud, API, tracking ou service distant ;
- aucune copie de `sylloge.db`, `sylloge.db-wal` ou `sylloge.db-shm` ;
- aucune restauration qui écrase un profil : on conserve l’import JSON existant dans un nouveau profil ;
- aucun changement de format d’export `sylloge-films` v1 ;
- aucun nouveau médium, redesign global, thème sombre ou nouvelle dépendance ;
- pas de planification en tâche de fond : le snapshot automatique se déclenche seulement après une mutation réussie dans l’application ouverte.

## Architecture retenue

### SQLite

Ajouter la migration séquentielle `0004_create_backup_settings.sql`, enregistrée dans `src-tauri/src/database.rs`.

La table doit être locale, minimale et liée au profil :

- `profile_id` clé primaire et référence vers `profiles` ;
- `backup_directory` non vide ;
- `last_automatic_snapshot_day` nullable au format `AAAA-MM-JJ` ;
- un horodatage de mise à jour.

La migration ne touche pas aux tables Films ni au format JSON. Les réglages d’un profil n’existent qu’après le choix explicite d’un dossier pour ce profil. Une migration séquentielle `0005_create_backup_snapshots.sql` enregistre ensuite les noms des snapshots que Sylloge a effectivement écrits, afin de sécuriser la rétention.

### Pont Rust

Étendre `src-tauri/src/portability.rs` et l’enregistrement des commandes dans `src-tauri/src/lib.rs` :

1. ouvrir un sélecteur **de dossier** natif ;
2. enregistrer ou mettre à jour le réglage du profil courant, avec validation que le chemin retourné est un dossier accessible ;
3. vérifier l’écriture du dossier puis écrire un snapshot JSON dans le dossier déjà enregistré ;
4. publier l’état ou le rapport nécessaire au frontend.

La commande d’écriture reçoit un document JSON déjà produit par le domaine, puis vérifie côté Rust : profil valide, dossier configuré et accessible, nom de fichier contrôlé. Écrire via fichier temporaire dans le même dossier puis renommage afin qu’un snapshot visible ne soit jamais un JSON partiel. Après une écriture réussie, appliquer la rétention du seul préfixe de ce profil ; ne jamais supprimer un autre fichier du dossier.

La commande qui décide un snapshot automatique ne doit marquer `last_automatic_snapshot_day` qu’après l’écriture atomique réussie. Le jour est calculé localement au moment de la demande. Les séquences de réglage et de sauvegarde sont sérialisées afin qu’un changement de dossier ne produise jamais un marquage incohérent.

### Frontend et domaine

- Réutiliser `createLibraryExport`, `serializeLibraryExport` et la validation JSON existante ; le snapshot ne duplique pas le modèle de données.
- Ajouter une passerelle typée dans `src/data/nativePortability.ts` et un service de sauvegarde étroit, injectable ou testable.
- Afficher le réglage et le bouton manuel dans `src/components/Portability.tsx`, sans cacher la différence entre export manuel, snapshot et synchronisation.
- Déclencher une tentative automatique **après** chaque mutation réellement réussie : création, modification, suppression et import. Ne pas annuler ou revenir en arrière sur l’opération métier si la sauvegarde échoue.
- Rendre les succès et échecs observables de manière non bloquante, y compris lorsqu’une mutation vient de se produire hors de l’écran « Profils et JSON ».

## Critères d’acceptation

1. Sans dossier choisi, l’écran explique que les sauvegardes ne sont pas actives et propose de sélectionner un dossier ; aucune écriture hors du dialogue d’export existant.
2. Le choix d’un dossier est explicite, persiste après relance et n’accorde pas d’accès générique au frontend.
3. Après le premier ajout, la première modification, la première suppression ou le premier import réussi d’un profil dans une journée, un JSON v1 valide est créé dans ce dossier.
4. Un second changement du même profil le même jour ne crée pas un second snapshot automatique ; le bouton manuel en crée bien un.
5. Chaque snapshot est lisible par `validateLibraryImport` et peut être restauré via le flux existant dans un nouveau profil.
6. Après le 31e snapshot d’un profil, les 30 plus récents restent ; seuls les snapshots Sylloge correspondants de ce profil sont supprimés.
7. Si le dossier est supprimé, renommé ou inaccessible, l’opération Films réussit ; un message visible indique l’échec et le prochain changement réessaie.
8. Aucune opération ne lit, copie, déplace ou synchronise les fichiers SQLite actifs.
9. Aucun ajout de dépendance, de permission Tauri générale, de source externe ou de migration non décrite dans ce document.

### Manuelles natives macOS

1. choisir un dossier test ;
2. créer puis modifier un film et constater un seul snapshot automatique ce jour-là ;
3. utiliser « Sauvegarder maintenant » et constater un nouveau snapshot ;
4. tenter d’importer un snapshot dans un nouveau profil ;
5. rendre le dossier indisponible, modifier un film et constater que la modification reste enregistrée tandis que l’alerte de sauvegarde s’affiche ;
6. relancer Sylloge et vérifier que le dossier reste configuré.
